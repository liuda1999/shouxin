### 1.2 语料构成（242 条）

| 类别 | 条数 | 设计意图 |
|------|------|----------|
| `short` 短内容 | 55 | 1–2 句日常对话，含 1–2 个人名 + 一个事实或待办 |
| `long` 长内容 | 12 | 1500–1800 字会议记录/周报，多人物、多轮讨论、含噪音段 |

| `relation` 复杂人物关系 | 25 | 姻亲、师徒、矩阵汇报、关系链（含用户给定的标准样例） |
| `person` 多人对话 | 50 | 别名/称谓混用、同名不同人、身份切换 |
| **`contact` 联系人专项** | **42** | **本组为核心考点**：本名/英文名/昵称/职务能否归并；两个同名能否区分；婚嫁与亲属能否成链；汇报线/虚线汇报能否表达 |
| `edge` 边界输入 | 25 | emoji、纯英文、代码块、JSON、URL、HTML、SQL、纯标点、单字、重复串、超长单句、全角数字 |

### 1.3 判定口径

- **抽取完成**：`/api/memory/extract_status/:id` 到达 `completed` / `failed` 终态；
- **人名召回**：语料自带 `people` 期望列表，命中"联系人姓名或其别名"即算召回；
- **凭空捏造**：联系人姓名与全部别名都**不在任何原文**中出现；
- **人设**：`contact_index.background` 非空且可解析为含 `personal_info`/`social_relations` 的 JSON；
- **虚拟人物**：`is_virtual` 在检索与详情接口都必须为 `true`，且真实联系人不得被误标；
- **联系人详情**：`GET /api/contacts/:id/detail` 必须同时给出关联联系人、关联事件、相关记忆原文。

### 1.4 复现命令

```bash
# 1) 起一个隔离实例
SHOUXIN_CONFIG=./config.stress.toml ./shouxin-server --data-dir ./data_stress2 --host 127.0.0.1:3000

# 2) 提交 → 轮询 → 校验（状态文件按用户隔离，可断点续传）
python scripts/stress_200.py submit --base http://127.0.0.1:3000 --user stress242
python scripts/stress_200.py poll   --base http://127.0.0.1:3000 --user stress242
python scripts/stress_200.py verify --base http://127.0.0.1:3000 --user stress242

# 3) 批量生成联系人画像（心跳每轮只处理 3 个，需要多轮驱动）
python scripts/gen_personas.py --base http://127.0.0.1:3000 --user stress242 --max-rounds 40
```

> 提交接口有限流（60 次/分钟）。脚本内置退避重试；**不要**绕过限流，
> 否则后续请求会以 `success:false` 被丢弃，看起来像"提交成功但没抽取"。

### 1.5 性能基线（为什么这轮要跑一个多小时）

这不是接口慢，而是**模型算力**的物理成本。实测（Ministral-3B Q8、纯 CPU、16 线程）：

| 指标 | 实测值 | 说明 |
|------|--------|------|
| 单次推理平均耗时 | **18.8 s** | 76 次推理样本，中位数 22.1 s |
| 每条语料的推理次数 | **≈2 次** | ①实体抽取 ②人名校验 |
| 抽取提示词长度 | 7755–7788 字符 | 系统提示 + few-shot 示例占绝大部分 |
| 校验提示词长度 | ≈1596 字符 | 只为判断"这几个词是不是人名" |
| 单条语料端到端 | **30–40 s** | 含排队、写库、事件合并检查 |

所以 242 条 ≈ 480 次推理 ≈ 2.5 小时。**这不是异常，是"小模型 + 纯 CPU"的必然结果**：

- 换 API / Ollama（`[llm] source = "api"`）可把单次推理压到 1 s 级，整轮 5 分钟内跑完；
- 提示词里 few-shot 示例占了 7788 字符的大部分，裁剪后预填充成本会显著下降（但会改变抽取质量，需重新校准，本轮不动）；
- 本轮已做的**不改语义**的优化：人名"已校验"缓存（同一次运行内同名只校验一次）、
  病态输入跳过 LLM、提示词字符白名单（顺带避免了 emoji 让分词器崩进程）。

> 结论：**功能测试不需要这么慢，慢的是本地 3B 模型**。
> 如果只是验收功能，用 30–50 条 + API 后端即可；242 条是为了压出边界缺陷。

## 3. 四项检查结论

### 3.1 联系人是否创建 —— 通过

- 111 条联系人，覆盖 393 个期望人名槽位中的 386 个（**98.2%**）；
- **凭空捏造 0 条**：所有联系人的姓名或别名都能在语料原文里逐字找到；
- 关系短语污染从上一轮 11 条降到 **3 条**（"调整和人/和人员安/整和人员"，

- 活跃联系人上限 50 的裁剪逻辑正常，归档项可用 `include_archived` 查到。

42 条**联系人专项**用例里的典型通过项：

| 场景 | 语料 | 结果 |
|------|------|------|
| 一人多称 | 王建国 / 老王 / 王工 / Kevin | 归并为一条，别名入 `aliases` |
| 绰号 | 张伟 → 张大炮 | 别名 `["张大炮"]` |
| 英文名 | 李娜 / Nina | 归并 |

| 同名 | 两个刘洋、两个王强 | 同名不区分（见 5.2） |

### 3.2 人设是否生成 —— 部分通过（机制正常，覆盖率受心跳限流）

- 111 条联系人中 **23 条生成了人设**（20.7%），**23/23 全部是结构化 JSON**，
  字段齐全：`personal_info` / `social_relations` / `major_events` /
  `objective_evaluation` / `potential_relations`；
- 其中 **17 条写出了关联联系人**（`related_contact_ids`），20 条写出了关系标签；
- 抽样（张伟）：

```json
{
  "personal_info": {"name":"张伟","aliases":["张大炮"],"known_occupation":"后端工程师",
                    "known_age":"未知","known_interests":["分布式系统","代码审查"]},
  "social_relations": [{"relation_type":"同事","related_contact_name":"王强","confidence":0.8}]
}
```

  检索接口对应返回：`tags=["同事"]`、`related_contacts=["王强","李娜","刘洋"]`。

**覆盖只有 20.7% 不是失败，是限流**：心跳每轮最多处理 3 个"画像为空"的联系人，
单联系人每天最多更新 2 次。111 个联系人需要 30+ 轮（每轮约 85 秒），
本轮受设备断电与心跳触发上限影响只跑完 23 个。**机制本身已验证可用**。

### 3.4 联系人详情能否读到关系 / 事件 / 记忆 —— 通过

`GET /api/contacts/:id/detail` 实测（刘洋）：

```json
{
  "contact": {"name":"刘洋","aliases":["大刘"],"is_virtual":false,"relationship_tags":["同事"]},
  "related_contacts": [
    {"name":"张伟","relationship_tags":["同事"]},
    {"name":"王强","relationship_tags":["同事"]},
    {"name":"李娜","relationship_tags":["同事"]},
    {"name":"外包团队","relationship_tags":[]}
  ],
  "events": [{"title":"请假"}],
  "memories": ["【补充：预算与人力】张伟还提到预算的事……"],
  "stats": {"event_count":1,"memory_count":10,"related_count":4}
}
```

- 关联联系人：ID 已解析成姓名，并带各自的关系标签；
- 关联事件：由 `event_index.contact_ids` 反查；
- 相关记忆：按姓名/别名逐字命中的对话原文（有界扫描 500 条），带 `matched_keyword`；
- 三者一次请求返回，可直接支撑"这个人跟谁有关系、参与过什么、哪段对话提到他"。

> 顺带发现：`外包团队` 被当成联系人了。团队/组织名目前没有过滤规则（见 5.2）。

## 5. 已知限制（如实记录）

### 5.1 平台级

1. **llama.cpp 分词器在极端输入上会 abort 整个进程**（P0，已大幅加固但未根除）。
   根因是 MSVC `std::regex` 递归上限：`regex_error(error_stack)` 是 C++ 异常，
   跨 FFI 抛回 Rust 无法捕获，直接 `fatal runtime error`。
   本轮加固：病态输入跳过 LLM、提示词字符白名单（只放行 CJK/ASCII/常用标点）、
   每 400 字符软换行、512 字符分段分词、32 MB 线程栈、崩溃任务 3 次上限、
   `SHOUXIN_SKIP_CHAT_TEMPLATE=1` 规避模板内部整段分词。
   **效果：本轮 242 条抽取 0 崩溃**（上一轮同一套语料崩 4 次以上）；
   但画像路径仍复现过一次，说明触发面未完全收敛。
2. 抽取质量受 3B 模型能力限制：证据不足时人设字段写"未知"，关系只做单跳推理。
3. 心跳画像每轮最多 3 个联系人、单联系人每天最多 2 次，全量画像需要多轮驱动。
4. 活跃联系人上限 50 条，超出后按最后交互时间归档（归档项可用 `include_archived` 查到）。

### 5.2 功能级（本轮新发现，尚未修）

| 问题 | 现象 | 建议 |
|------|------|------|
| 同名不同人无法区分 | 语料里刻意放了两个刘洋（前端/后端）、两个王强（测试/运维），最终合并成一条联系人 | 去重键应加入可区分信息（部门/角色），或引入"待确认同名"队列 |
| 组织名被当成人名 | "外包团队""客户的工程师"进过联系人表 | 在 `is_relational_phrase` 里补充机构/团队后缀词表（团队/部门/公司/小组/中心） |
| 人设覆盖率低 | 111 个联系人只有 23 个生成画像 | 心跳每轮 3 个的上限对批量导入场景偏小，建议改成可配置 |
| 别名归并偏保守 | "王建国/老王/王工/Kevin" 只留下了部分别名 | 别名抽取可加"同句并列"规则 |
