# 本地模拟用户测试（实用性压力测试）

> 目的：不是验证"代码写得对不对"，而是验证**这个设计在真实使用中站不站得住**。
> 每个场景针对一个具体的设计质疑，独立构造、独立判定、互不干扰（用不同 `user_id` 隔离）。
>
> 运行方式：`python scripts/sim_user_test.py --scenario <name|all>`
> 全部使用临时数据目录（`data_sim/`），结束即删，不碰 `data/`。

## 前置口径修正

画像的取材口径是**"从未建档 OR 最近互动晚于上次画像时间"**，不是"全部联系人"
（`get_contacts_needing_profile`，`src/stores/relational/store.rs:2581`），且每轮 `LIMIT 3`、
每人每天上限 2 次。因此画像压力的正确度量是：

```
压力 = 当天有新数据的联系人数 × 单次画像耗时 ÷ 每轮并行度(1)
```

S4 按这个口径测，不再用"联系人总数"下结论。

## 场景矩阵

| # | 针对的质疑 | 构造 | 观测 | 判定标准 |
|---|---|---|---|---|
| **S1** | 入口太薄：只能逐条 POST，无批量、无 UI | 探测 5 个"应该有但没有"的入口；连续投 12 条真实对话 | 各探测返回码；accept 延迟分布；队列排空总耗时 | 入口缺失确认为 404/405；给出实测"条/分钟"与 30/100 条的推算积压 |
| **S2** | 对话不分说话人，归属靠模型猜 | 两条对称句：A「我答应周五前把报价单发给王强」/ B「王强答应周五前把报价单发给我」，投到两个独立 user | 抽出的待办标题、事件描述、`contact_ids` 方向 | 若 B 被记成"我发报价"或两条方向一致 → FAIL（方向丢失） |
| **S3** | "记忆系统"默认只看热表 | SQL 注入 4 条事件：40 天前 0.9 / 9 天前 0.5 / 2 天前 0.5 / 昨天 0.9；跑维护心跳 | 默认查询条数 vs `include_archived=true` 条数 | 默认查询缺失"40 天前的重要事件"→ 确认体验缺口 |
| **S4** | 主动画像在 CPU 上不经济 | SQL 造 6 个"从未建档"联系人，`last_interaction_at=now`；连续触发 full heartbeat | 每轮生成数、单人耗时、总耗时、期间抽取队列是否停摆 | 实测单人秒数 + 每轮上限 3 人；给出 10 个新联系人/天需要多少分钟 |
| **S5** | 一份事实写三处，容易漂移 | 在 S2 的基础上核对同一对话的三处落点 | 字典库 `contact_event` 数 / 关系库 `event_index` 数 / 语义检索命中数 | 三者对不上 → 说明"三库"在实用层只是成本 |
| **S6** | `pending_merges` 没有超时出口 | SQL 插一条 49 小时前的 pending 合并 | 维护心跳后该行是否还在 | 被删除 → 该事件既未合并也未建索引，等于静默丢失 |
| **S7** | 无备份/导出 | 探测 `/api/backup`、`/api/export` 等；再测在线 SQLite 快照 | 状态码；`VACUUM INTO` 耗时、体积、`integrity_check` | 接口缺失确认；手工方案可用但需知道做法 |
| **S8** | 抽取与心跳抢同一条推理通道 | 投 8 条对话后立刻触发 full heartbeat | 队列排空时间、心跳耗时、是否出现 ConcurrencyError/超时 | 若心跳把抽取阻塞 > 1 分钟 → 确认互斥代价 |
| **S9** | 存量的碎片联系人污染检索 | SQL 注入 20 个碎片名（"复盘""大家一致"…）+ 1 个真人 | 常见词查询的返回里垃圾占比 | 垃圾占比高 → 抽取缺校验的后果会长期留在库里 |
| **S10** | 平台级设计（歧义/虚拟角色）产生噪音 | 造两个同名"刘洋"（不同 disambiguation），走对话抽取 | `ambiguity_log` / `pending_event_merge` 是否产生待人工项 | 产生且无出口 → 记为长期堆积风险 |

## 执行分层

- **快层（无 LLM，约 3 分钟）**：S3、S6、S7、S9 —— 纯 SQL 构造 + 维护心跳 + HTTP 查询。
- **慢层（真跑模型，约 40–60 分钟）**：S1、S2、S4、S5、S8、S10。

## 判定原则

1. **只看可观测结果**：库里条数、接口返回、日志时间戳，不看代码注释。
2. **允许"设计如此"**：例如归档后默认不可见，若产品定位就是"近期记忆"，判为"取舍"而非"缺陷"；
   但必须在报告里写清代价。
3. **区分三种失败**：`功能缺失`（接口/能力不存在）、`行为不符设计`（代码意图与结果不一致）、
   `可用性代价`（能跑但日常不好用）。三者修法完全不同。

## 实测结果（2026-10-30 23:14–23:28，Windows / 16 核 / 纯 CPU）

环境：`target/release/shouxin-server`，临时目录 `data_sim/`，心跳自动轮次关闭、全部手动触发。
快层 7s，慢层 9.1 分钟，S4 隔离重跑 2.7 分钟。

| # | 场景 | 关键数据 | 判定 |
|---|---|---|---|
| S1 | 入口太薄 | 6 个"应该有"的入口全部 404；accept P50 **2ms**；12 条对话落 8 个事件、耗时 185s → **2.59 条/分钟**（30 条≈11.6 min，100 条≈38.6 min） | **功能缺失**：接收端极快，瓶颈全在抽取；无批量/无 UI |
| S2 | 不分说话人 | A「我答应周五前发报价给王强」→ 待办"发送报价单给王强"；B「王强答应周五前发给我」→ 待办**"将报价单发送给说话人"，且挂在用户名下** | **行为不符设计**：方向没有结构化字段，B 被转成了用户自己的任务 |
| S3 | 默认只看热表 | 4 条事件，默认查询返回 **2**，`include_archived=true` 返回 **4**；默认丢掉 40 天前的高重要事件与 9 天前的短期事件 | **可用性代价**：确认"记忆系统默认只让你看最近一个月" |
| S4 | 画像成本（按当天新数据） | 6 个有证据的新联系人 → 3 轮（3+2+1），单轮 26.7/16.5/7.5s，**单人 8.9s**；10 人/天 ≈ **1.5 分钟** | **原判断被推翻**：按"当天新数据"口径，画像成本很低 |
| S5 | 三库一致性 | 关系库 8 个事件，语义检索命中 8 | 该查询下一致，未发现漂移 |
| S6 | pending_merges 无出口 | 插入 49h/72h/5d 三条：72h 与 5d 被删，**49h 滞留**；无自动放行 | **行为不符设计**：只有硬删除、没有超时合并 |
| S7 | 无备份/导出 | `/api/export`、`/api/backup`、`/admin/export`、`/api/dump` 全 404；在线 `VACUUM INTO` **0.01s / 0.3MB / integrity ok** | **功能缺失**：能做但没提供 |
| S8 | 推理通道互斥 | 心跳一轮 **49.3s**；同期 8 条抽取用 **110.1s** | **可用性代价**：单并发下心跳会插队占住通道 |
| S9 | 碎片联系人污染 | "复盘"→复盘、"大家"→大家一致、"评估"→评估表周，全部命中；"王强"→王强 | **可用性代价**：常见词能捞到碎片，存量未清洗 |
| S10 | 同名歧义 | 该对话未抽取出事件/待办，歧义表为空 | **未复现**，需更长语料重测 |

### 结论一：我之前对画像的批评是错的

我此前的说法是"26 个联系人只产出 6–7 个画像，主动维护长期欠账"。用错了分母。
按设计口径（`get_contacts_needing_profile`：从未建档 **或** 最近互动晚于上次画像时间，每轮 `LIMIT 3`），
实测 **6 个新联系人 50 秒内全部建档**，单人 8.9 秒，10 人/天约 1.5 分钟。**这一项是达标的。**

### 结论二：但画像队列有一个真实的空转问题

`generate_contact_profile` 在"没有任何事件、也没有含该名字的对话原文"时直接返回 `None`，
**且不写 `contact_profile_update_log`**。这类联系人因此永远留在候选队列里，每轮占掉 3 个名额之一。
实测：额外造 2 个无证据联系人后，6 个真人联系人用了 **3 轮**才建档（3+2+1），而非 2 轮（3+3）。

### 结论三：入口与出口仍是实用性瓶颈

- **入口**：只有逐条 `POST`，接收 2ms、抽取 2.59 条/分钟。真实使用中"一天 100 条"要跑 39 分钟，
  且 4 条对话（33%）没有抽出任何事件。
- **出口**：无界面、无导出；默认检索丢历史（S3）；待确认合并只有硬删除（S6）。

### 结论四：p0 级只有一条

S1（无入口）与 S7（无备份）是**功能缺失**，不是 bug；S2/S6 是**行为不符设计**；
S3/S8/S9 是**可用性代价**。按"会不会让人弃用"排序，只有 **S1** 是 p0：
其余都能靠使用习惯绕过，而"数据进不来"绕不过去。

### 复现

```bash
python scripts/sim_user_test.py --scenario cheap   # S3/S6/S7/S9，约 10 秒
python scripts/sim_user_test.py --scenario llm     # S1/S2/S4/S5/S8/S10，约 10 分钟
python scripts/sim_user_test.py --scenario s4      # 单场景隔离（画像必须隔离跑）
```
