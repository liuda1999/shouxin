## 三、阻塞级问题（第一次用就会被绊到）

### B-1 待确认合并列表全是误报，且点"合并"没有任何实际效果

**现象**

我存了 17 条内容差异很大的对话，系统给出 5 条待确认合并。看内容：

| 源事件 | 目标事件 | 相似度 |
|---|---|---|
| 写成可以直接照着改的修复清单 | 用户让我把守心 v0.7.3 的测试报告精简一下 | 0.904 |
| 清单写完了，放在 docs/FIX_P0_P1_v0.7.3.md | *同上* | 0.909 |
| 用户把项目更新到了 0.7.6 | *同上* | 0.914 |
| 用户要求我忘掉之前测试踩过的坑 | *同上* | 0.903 |
| 11 月 12 号前把明年的预算表定下来 | *同上* | 0.906 |

**5 条的目标事件是同一条**，而源事件之间毫无关联（"预算表"和"测试报告精简"分明是两件事）。

然后我点了合并：

```
POST /api/events/pending_merges/4/resolve  {"action":"merge"}
  -> 200 {"resolved": true, "event_id": "b7c54a01-..."}
POST /api/events/confirm_merge  {"merge_id":3,"action":"merge"}
  -> 200 {"success": true, "message": "事件已合并"}

event_index 条数：合并前 6  ->  合并后 6
```

两个端点都返回成功，事件表里一条没少、一条没变。

**根因（三处叠加）**

1. **源事件 id 是伪造的** —— `three_library_manager.rs:687`：

   ```rust
   let source_event_id = format!("pending_{}", uuid::Uuid::new_v4());
   ```

   源事件本身其实正常入库了，但待确认表里记的是这个凭空生成的 id。用户点合并时，系统拿 `pending_xxx` 去找源事件、删源事件、更新目标事件 —— 全都找不到，所以什么都不发生，还返回成功。

2. **阈值没读配置，是硬编码的** —— `three_library_manager.rs:664 / 682`：

   ```rust
   if similarity > 0.90 { ... 自动合并 ... }
   else if similarity > 0.75 { ... 进待确认区 ... }
   ```

   `config.toml:128-129` 写的是 `event_merge_auto_threshold = 0.96` / `event_merge_pending_threshold = 0.90`，那套只在 `background_queue.rs:111` 生效（日志里 `[P1-7]` 打印的"阈值 0.90-0.96"就是它）。**事件实际落库走的是 manager 这条路径，用的是硬编码的 0.90/0.75，改配置没用。**

3. **相似度分布贴着阈值** —— 实测 5 条全部落在 0.902–0.914 的窄带里，内容跨度却极大。这个 embedding 对短文本的区分度不够，0.90 的线正好切在分布中间，于是"什么都进待确认区"。

**改法**

- ① 记录真实源事件 id：把 `insert_pending_event_merge` 的调用放在事件插入成功之后，用真实的 `event_id`，删掉 `pending_{uuid}` 的构造。
- ② 阈值统一：`three_library_manager` 也从配置读，删掉硬编码的 0.90/0.75（或至少让两处共用同一个 `MERGE_THRESHOLDS`）。
- ③ 合并结果要可验证：`confirm_pending_event_merge` 用 `rows_affected` 判断，影响行数为 0 就返回失败，不要返回"事件已合并"。
- ④ 顺带：`event_summary_for_merge` 是 `format!("{} {}", title, description)`（`three_library_manager.rs:643`），而 description 常常以 title 开头，等于把标题说了两遍（日志里能看到"写成可以直接照着改的修复清单 写成可以直接照着改的修复清单。"）。去重前先去掉这种重复，能顺手压低虚高的相似度。

**验收**：造 3 条内容无关 + 1 条内容重复的事件；无关的不进待确认区；重复的进区后点合并，`event_index` 条数减 1、目标事件描述被更新、接口返回真实影响行数；再点一次同一 id 应报"已处理"。

### B-2 兜底抽取的事件标题从词中间切开

**现象**

原文：`提醒我 6 月 24 号之前把年中总结交上去。`
落库事件标题：**`醒我 6 月 24 号之前把年中总结交上去`** —— 开头的"提"被吃掉。

待办标题（同一句话抽出来的）是对的，叫"年中总结"。所以只有事件标题坏了。

**根因** —— `extractor.rs:1621-1639`：

```rust
const MAX_LEFT: usize = 16;
let mut start = kw_start.saturating_sub(MAX_LEFT);
if let Some(pos) = (start..kw_start).rev().find(|&i| STOP.contains(&chars[i])) {
    start = pos + 1;          // 找到句读就用句读
}
```

关键词是"总结"，位于第 17 字；向左找句读找不到（它就在句首附近），于是硬回退 16 字 → 从第 1 字开始 → "醒我…"。

代码注释里写着这个问题已经处理过（"不要再固定左移 8 字：8 字会正好切在词中间"），**但改法只是把 8 换成 16，机制没变**——只要关键词离句首超过 16 字，照样从词中间切开。

**触发条件**：模型返回 `events: []` 时走兜底。这条对话模型只抽出了 todo，日志里 `Raw response: {"people":[],"events":[],"todos":[...]}`，于是兜底造了一条事件。

**改法**：找不到句读时，回退到句子开头而不是固定字数。最省事的一版——

```rust
let mut start = 0;   // 找不到句读就从整句开头取，宁可长也不要半截词
if let Some(pos) = (0..kw_start).rev().find(|&i| STOP.contains(&chars[i])) {
    start = pos + 1;
}
```

若担心标题过长，再对 `end` 侧截断（当前已限制 `end - kw_start < 24`），别动左侧。

**验收**：`提醒我 6 月 24 号之前把年中总结交上去。` → 标题以"提醒我"开头；再试"今天又和张伟确认了预算表"这类句首无标点的句子，标题不从词中间起。

## 四、明显影响体验

### N-1 心跳生成的待办质量差且重复

心跳给我生成了两条待办，是同一段"需要澄清"的内容：

- 标题 1：`需要澄清：SelfContradiction`，deadline 11-04
- 标题 2：`澄清: 存在多处不确定信息和潜在的自我矛盾。首先，用户在14:40:00的请求中要求"忘掉之前测试踩过的坑，……`（132 字，整段 detail 直接当标题）`，deadline 11-08

一条待办的标题是 132 字的整段分析；两条是同一件事；待办列表里它们和普通待办混在一起，用户根本没法扫。

`/api/heartbeat/pending_questions` 同样给了 2 条，内容几乎逐字重复，而且 `category` 是 `EntityDisambiguation`、标题却写 `SelfContradiction`，分类和标题对不上。

**建议**：待办标题单独生成（限 20 字内，detail 放描述字段）；同一 `detail` 去重；`category` 与标题取同一个来源。

### N-2 事件标题碎片化，读不懂

从 17 条对话里抽出的事件标题包括：`而不是对着清单验收`、`历史导入会差一年`、`说 5 条 P1 都按清单改完了`。

单看这些标题不知道在说什么，得点开 description 才明白。这些是模型直接给的标题，不是兜底产物。

**建议**：提示词里对 title 加约束（必须能独立成立的主谓宾短句，不承接上下文、不以连词开头）。

### N-3 文件上传接口不按常见惯例

- 必须 `Content-Type: application/octet-stream` 发原始字节流；用 `multipart/form-data` 返回 415，并提示"不支持 multipart"（信息清楚，这点是好的）。
- `filename` 必须放 query string，放 form 字段里报 400 `missing field filename`。

第一次接的人大概率要试两次。**建议**：文档里把这三点写进示例（现有示例只有一行 curl，看不出要发原始流）。

## 五、小瑕疵

- **事件时间取的是截止日而非发生日**：`6 月 24 号之前交年中总结` 的事件时间记为 06-24 00:00，而不是对话当天 06-10。语义上可辩护，但和待办 deadline 撞在同一天，时间轴上会叠在一起。
- **联系人别名基本为空**：本次抽取出来的真人（王建国等）`aliases` 全是 `[]`，只有种子里的虚拟角色有别名。真人别名没有被收集。

## 六、复现方式

```bash
# 独立实例
sed -e 's|^port = 3000|port = 3110|' \
    -e 's|^data_dir = "./data"|data_dir = "E:/tmp/t1/data"|' \
    config.toml > /tmp/t1/config.toml
SHOUXIN_CONFIG=/tmp/t1/config.toml ./target/release/shouxin-server.exe

# B-1：写入 5 条内容无关的对话 -> 查待确认列表 -> 点合并 -> 数 event_index
curl -s "http://127.0.0.1:3110/api/events/pending_merges?user_id=me&scope=user"
sqlite3 E:/tmp/t1/data/shouxin.db "select count(*) from event_index;"

# B-2
curl -s -X POST http://127.0.0.1:3110/api/memory/batch -H 'Content-Type: application/json' \
  -d '{"user_id":"me","scope":"user","items":[
        {"conversation":"提醒我 6 月 24 号之前把年中总结交上去。","timestamp":"2026-06-10 10:00:00"}]}'
# 抽取完成后
sqlite3 E:/tmp/t1/data/shouxin.db "select title from event_index order by created_at desc limit 1;"
```

## 七、如果只修两处

1. **B-1**（真实源 id + 阈值统一）—— 否则去重功能等于没有，用户还会被噪音列表淹没。
2. **B-2**（标题别从词中间切）—— 一行改动，兜底路径触发率不低，标题是用户第一眼看到的东西。
