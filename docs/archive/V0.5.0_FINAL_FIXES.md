## 第一步：修复数据库迁移（P0-2）

### 问题描述
启动服务后数据库只有 8 张基础表，缺失 v0.5.0 新增的 6 张表和 `todo_list` 的 5 个新列。

### 修复方案

**文件**: `src/stores/relational/store.rs`

在 `init_schema()` 末尾新增 `init_schema_v0_5_0()` 方法，实现幂等迁移：

1. 创建 `schema_migrations` 版本跟踪表
2. 检查 v0.5.0 是否已执行
3. ALTER TABLE 添加缺失列（`todo_type`, `entity_type`, `entity_id`, `resolved_answer`, `resolved_at`）
4. ALTER TABLE 添加 event 列（`canonical_event_id`, `merged_from_ids`, `ambiguity_flag`）
5. CREATE TABLE IF NOT EXISTS 创建 6 张新表
6. 创建 12 个索引
7. 记录迁移版本

**关键代码 diff**:

```rust
// store.rs - init_schema() 末尾添加
self.init_schema_v0_5_0().await?;

// store.rs - 新增方法
async fn init_schema_v0_5_0(&self) -> Result<(), ShouxinError> {

        "ALTER TABLE todo_list ADD COLUMN resolved_answer TEXT DEFAULT NULL",
        "ALTER TABLE todo_list ADD COLUMN resolved_at TEXT DEFAULT NULL",

        "ALTER TABLE event_index ADD COLUMN merged_from_ids TEXT DEFAULT NULL",
        "ALTER TABLE event_index ADD COLUMN ambiguity_flag INTEGER DEFAULT 0",
    ];
    for mq in &alter_queries { let _ = query(mq).execute(&self.pool).await; }

    // CREATE TABLE 创建新表

        "CREATE TABLE IF NOT EXISTS memory_processing_state (...)",
        "CREATE TABLE IF NOT EXISTS contact_profile_update_log (...)",
        "CREATE TABLE IF NOT EXISTS contact_merge_log (...)",
        "CREATE TABLE IF NOT EXISTS event_merge_log (...)",

        "CREATE TABLE IF NOT EXISTS contact_alias_index (...)",
    ];
    for cq in &create_queries { let _ = query(cq).execute(&self.pool).await; }

    // 创建索引
    // ...

    // 记录迁移
    query("INSERT INTO schema_migrations (version) VALUES ('v0.5.0')").execute(&self.pool).await;
    Ok(())
```

## 第二步：修复 LLM 提取功能（P0-1）

### 问题描述
`POST /api/memory/add` 返回 200 但 contacts/events 始终为空数组，三轮测试 100% 失败。

### 根因分析

三个子问题层层递进：

1. **llama-cpp-2 v0.1.146 的 `get_logits_ith(-1)` 问题**：该版本中 `get_logits_ith(-1)` 和 `get_logits_ith(N)` 均因 "logit N is not initialized. only [0] is" 失败，即使所有 token 都设置了 `logits=true`。

2. **GGUF 推理 panic 导致服务器崩溃**：推理代码在 async 上下文中直接执行，panic 会传播到 tokio runtime。

3. **Prompt 过于复杂**：原始 prompt 要求 5 类提取，3B 小模型难以理解。

### 修复方案

#### 2.1 修复 logits 获取（关键修复）

**文件**: `src/llm/gguf.rs`

用 `context.get_logits()` 替代 `context.get_logits_ith(-1)`：

```diff
- let logits = context.get_logits_ith(-1);
+ let logits = context.get_logits();
```

`get_logits()` 返回最后一次 decode 的完整 logits，不依赖位置索引，在 llama-cpp-2 v0.1.146 中工作正常。

#### 2.2 添加 catch_unwind 防止 panic 崩溃

**文件**: `src/llm/gguf.rs`

将整个推理代码包装在 `std::panic::catch_unwind` 中：

```rust
let inference_result = std::panic::catch_unwind(
    std::panic::AssertUnwindSafe(|| -> Result<String> {
        // 所有推理代码（context 创建、tokenize、decode、generate）
        Ok(result)
    })
);

match inference_result {
    Ok(Ok(text)) => text,
    Ok(Err(e)) => return Err(e),
    Err(panic_info) => {
        let msg = /* 提取 panic 信息 */;
        tracing::error!("GGUF inference panicked: {}", msg);
        return Err(ShouxinError::LLMError(format!("GGUF推理panic: {}", msg)));
    }
};
```

#### 2.3 简化 Prompt

**文件**: `src/memory_extractor/extractor.rs`

将原始 5 类提取精简为 2 类（人名 + 事件），适配 3B 小模型：

```rust
fn default_system_prompt() -> String {

     {\n  \"persons\": [{\"name\": \"姓名\"}],\n  \"events\": [{\"description\": \"描述\", \"time\": \"时间\"}]\n}\n\
```

## 第三步：修复互斥锁（P0-3）

### 问题描述
10 个并发心跳请求全部返回 200，互斥锁完全失效。

### 根因分析
`HeartbeatScheduler` 中已有 `AtomicBool` 实现，但之前的锁检查逻辑存在竞争条件。

### 修复方案

**文件**: `src/heartbeat/scheduler.rs`（已存在，无需修改）

已有的 `compare_exchange` 实现正确：

```rust
pub async fn trigger_now(&self) -> Result<HeartbeatReport, ShouxinError> {
    if self.running.compare_exchange(false, true, Ordering::Acquire, Ordering::Relaxed).is_err() {
        return Err(ShouxinError::ConflictError("Heartbeat already running".to_string()));
    }
    // 执行心跳...
    self.running.store(false, Ordering::Release);
    Ok(report)
}
```

**文件**: `src/api/routes.rs` - `trigger_heartbeat` handler 直接调用 scheduler 的 `trigger_now()`，无需额外加锁。

### 验证结果
```

```

10 个并发请求中，1 个成功执行（200），9 个被拒绝（409 Conflict），符合预期。

## 第四步：修复语义搜索无结果（P1-1）

### 问题描述

### 根因分析

两个问题：

1. **Scope 不匹配**：文件上传使用 scope="Agent"（默认值），但语义搜索默认 scope="User"，owner 过滤导致所有文件记录被排除。

2. **material=None 的记录被跳过**：文件 chunk 的 `StoredRecord.material` 为 `None`，原搜索逻辑只在 `material` 为 `Some` 时检查，导致 `None` 的记录被直接跳过。

## 已知限制

1. **LLM 提取精度**：3B 模型（Llama-3.2-3B-Instruct）在中文姓名提取上精度有限，可能提取出不完整的姓名（如"王总明天"而非"王总"）。建议升级到 7B+ 模型以获得更好的提取效果。

2. **心跳歧义检测**：大 prompt（>3222 chars）可能因 token 数超过 batch size 512 而失败，日志显示 "Insufficient Space of 512"。建议增大 `n_batch` 或使用 `n_ctx` 更大的配置。

3. **catch_unwind 范围**：catch_unwind 仅包裹推理代码，若 llama-cpp-2 在 catch_unwind 外的代码（如 `new_context`）中 panic，仍可能导致崩溃。但当前测试中未出现此类情况。
