# 守心 · 设计认知确认书

> 目的：在动手修复前，先确认我对项目"设计追求"的理解是否与你的原意一致。
> 说明：以下"设计契约"是我从 `PROJECT_INTRO`、`TECHNICAL_DOCUMENTATION`、`FEATURE_MODULES_CN`、`ASYNC_EXTRACT_DESIGN` 与代码实现中反推出来的；标 ❓ 的是我不确定、需要你拍板的点。

---

## 一、项目定位：它到底在解决什么问题

守心不是"笔记软件"，也不是"通用知识库"，而是一个**个人认知记忆系统**：

- 输入是自然对话，不是结构化表单；
- 系统负责把对话**自动拆解**成人物、事件、待办、事实、学习素材；
- 数据**只在本机**，LLM 与 embedding 都本地跑；
- 系统会**自己维护自己**（心跳清理、合并、提问），而不是等用户手动整理。

**设计价值观（我理解的优先级）**：

1. **可信存档 > 查询性能**：原始数据必须先安全落盘，索引慢一点可以接受。
2. **自动化 > 手动整理**，但自动化不能牺牲可解释性——所以要有状态、错误、问题池。
3. **本地优先 > 功能丰富**：不引入云依赖，不把数据交给第三方。
4. **渐进降级 > 直接失败**：LLM 失败降级正则，主后端失败切备用。
5. **有界资源 > 无限增长**：热表上限、内存阈值、队列/归档。
6. **可演进 > 一次做对**：配置化、trait 扩展、双后端可切换。

如果这六条里有一条不是你的原意，后面的修复排序就要改。

## 二、三库架构：不是"三个数据库"，而是"权威 + 派生"

我理解的三库职责边界：

| 库 | 角色 | 数据性质 | 关键契约 |
|----|------|----------|----------|
| 字典库（Sled） | **权威原始存档** | 对话原文、`ContactTotal`、`ContactEventRecord`、文件全文 | 只追加、不因索引重建而丢失；是 source of truth |
| 关系库（SQLite） | **可重建的结构化索引** | `ContactIndex`、`EventIndex`、`TodoItem`、`FileIndex`、别名、待合并 | 支持查询/过滤/冷热分离；坏了可以从字典库重建 |
| 向量库（HNSW/Embedded） | **可重建的语义索引** | 学习素材、事件 embedding | 支持相似度检索；删除/失效必须跟随源数据 |

**由此推出的最重要设计契约**：

> 字典库完整 → 关系库/向量库只是"视图"。
> 任何写路径都必须保证"字典库字段完整、事件历史不丢"，否则不是普通 bug，而是**权威存档被污染**。

这就是为什么我把 F-M1（联系人业务字段被清空）、F-M2（事件历史缺失）列为 P0，而不是"数据小问题"。

❓ **需要确认**：字典库是否严格 append-only？文件全文删除、事件归档时，字典库是否允许物理删除？还是只删索引、字典永远保留？

## 三、写入主链路：同步与异步必须"语义等价"

设计链路：

```
POST /api/memory/add
  → 原文立即落字典库（零丢失）
  → 入队（sled 持久化）
  → 立即返回 conversation_id
  → 后台：LLM 提取 → 清洗 → 分发三库 → 状态 completed/failed
```

我理解的设计契约：

1. **返回前原文必须已持久化**（零丢失）。
2. **异步路径与同步路径必须产生相同的三库结果**——否则"异步化"只是把 bug 藏到后台。
3. **失败必须可观测**（status + error），不能静默。
4. **重启后 pending 可恢复**。
5. **三库写入要么全成，要么可补偿**；不要求分布式强事务，但不能留下"一半写入 + 状态 completed"。

**现实偏离**：v0.5.1 异步化时，worker 自己重写了一套写库逻辑（`write_extraction_results`），没有复用 `DataDispatcher`。于是出现 F-M1/F-M2/F-M3/F-M4，以及 F-X4/F-X5（异步没有 0.98 去重、没有质量过滤）。

**我的判断**：正确方向不是"在异步路径继续打补丁"，而是**抽一个统一的 MemoryWriter（或让 worker 复用 DataDispatcher）**，让两条路径共享同一套写入语义。这也是我建议的第一阶段。

❓ **需要确认**：你是否接受"抽统一写入层"这种中等规模重构？还是希望先做最小补丁、把重构留到升级阶段？

## 四、Owner / Scope：隔离是"设计目标"，不是"可选字段"

我理解的模型：

- `Scope`：`User` / `Agent`；
- `OwnerType`：`User` / `Agent` / `Contact` / `Public`；
- 所有业务表都有 `owner_type + owner_id`，用于**隔离**，不是装饰字段。

设计契约：

1. 所有写入必须带正确 owner；
2. 所有读取/删除必须校验 owner（至少不能任意 id 越权）；
3. owner 身份的来源必须**唯一**——应该来自配置 `primary_agent_id`，不能多处硬编码；
4. `owner_type` 的序列化表示必须统一（`User`/`Agent`，而不是有的地方 `user`/`agent`）。

**现实偏离**：
- `"primary_agent"` 与 `"primary_agent_default"` 两套值并存（F-T1）；
- `ContactRecord` 没有 owner_type，trait 实现硬编码 `User`（F-M3）；
- 文件表用小写 `user/agent`（F-F6）；
- 文件 get/delete、向量 get、事件 confirm 都没有 owner 校验（F-F3/F-VS2/F-E3）。

❓ **需要确认**：Agent 的唯一权威 owner_id 到底是配置里的 `primary_agent_id`（默认 `primary_agent_default`），还是历史沿用的 `"primary_agent"`？这决定 F-T1 是"改配置默认值"还是"改代码调用点"。

## 五、记忆生命周期：热/冷/失效/提升，是一套"有界资源"机制

我理解的设计意图：

- 热表有界（事件 200/100，联系人 50，待办 50/30）；
- 冷数据**软归档**（`is_archived`），不是物理删除；
- 事件有 `auto_invalid_at`，到期失效；
- 被频繁引用的事件可以**提升**，长期不用可以**降级**；
- 提升/降级必须发生在清理之前，避免"刚被引用就被归档"。

设计契约：

1. 归档是软删除，冷数据仍可查（`include_archived`）；
2. 清理规则明确、可解释、可配置；
3. 提升/降级顺序正确；
4. 阈值不写死。

**现实**：顺序正确、软删除正确；但阈值大量硬编码（F-T3/F-H4），`update_todo_deadline` 不更新 `last_updated_at` 会让刚改期的待办被误归档（F-T4）。

❓ **需要确认**：冷数据（归档）默认是否参与普通搜索？`include_archived` 的默认语义是"不包含"还是"包含"？

## 六、心跳：系统的"自主维护"，不是"定时任务"

我理解的心跳设计：

- **维护阶段**：纯 SQL、快、绝不调用 LLM（清合并、提升降级、清过期、孤儿向量、联系人归档、待办失效/归档/提醒）；
- **LLM 阶段**：慢、分析画像、发现歧义、生成问题；
- 两阶段可独立触发（`maintenance_only`）；
- 并发互斥（409），`ExecutingGuard` 保证异常也能清标志；
- 可关闭、可调频、可自适应、低内存时跳过。

设计契约：

1. 维护阶段不碰 LLM；
2. `enabled=false` 必须真的不启动；
3. `min/max/adaptive/idle` 要么实现，要么删掉，不能"配了不生效"；
4. 失败不能卡死 `executing`；
5. 心跳的问题池、画像、日志要可追溯。

**现实**：拆分、Guard、409 都正确；但 `enabled` 从未读取（F-H0），`min/max/adaptive/idle` 传入后未使用（F-H1），`question_pool_dir` 被硬编码覆盖（F-H2），超时/阈值硬编码（F-H3/F-H4）。

❓ **需要确认**：自适应间隔是本版本必须实现的能力，还是可以先降级为"固定间隔 + 可配置"？

## 七、LLM：本地优先、可切换、输出不可信

我理解的设计：

- 三后端：GGUF（本地默认）/ Ollama / OpenAI 兼容 API；
- `LlmClientManager` 负责主备切换、健康检查、重试、预加载；
- 心跳有独立 LLM 后端（`[llm.heartbeat]`）；
- LLM 输出**不可信**：必须 sanitizer + JSON 修复 + 正则兜底。

设计契约：

1. 本地 GGUF 是默认路径，不能被迫联网；
2. 主备切换不改变请求语义；
3. 超时/重试/健康检查策略必须一致且可配置；
4. 心跳 LLM 与主 LLM 隔离，心跳失败不能拖垮主链路；
5. 输出异常时必须降级，而不是把乱码写进库。

**现实**：架构完整；但 GGUF 内部 180s 与配置 600s 不一致（F-L1），Ollama/API timeout 未完全走配置（F-L2），失败阈值/健康检查间隔硬编码（F-L3）。

❓ **需要确认**：超时语义以哪一层为准——LLM 客户端层（180s/600s），还是提取流水线层（`[extraction].timeout_secs`）？两层是否需要统一成一个值？

## 八、外围能力：文件 / 虚拟实体 / 事件合并，是"记忆质量保障"

我理解它们不是独立功能，而是保证记忆质量的三个闸门：

- **文件**：原始字节 → 文本 → 分块向量；元数据同步、文本异步；MD5 去重；
- **虚拟实体**：避免把林克/ChatGPT 当真人；别名机制；内置角色；
- **事件合并**：语义去重；>0.90 自动合并，0.75–0.90 待确认。

设计契约：

1. 派生数据（向量/索引）删除时必须跟随清理；
2. 合并/去重失败不能丢原始数据；
3. 虚拟实体不进入真人联系人体系；
4. 文件原始字节与提取文本都要可追溯。

**现实**：文件删除留孤儿向量/临时文件（F-F8/F-F2）；事件合并失败会丢源事件（F-E6/F-E7）；虚拟实体别名替换无事务（F-V1/F-V2）。

❓ **需要确认**：文件向量删除时，是物理删除，还是标记失效、由心跳统一清理？

## 九、我对"修复"的理解与边界

我理解的修复不是"逐个改 bug"，而是**恢复设计契约**，顺序应该是：

1. **统一写入语义**（消除双路径，修 F-M1~M5、F-X4/X5）；
2. **统一 owner/scope**（修 F-T1/T2、F-M3、F-F3/F6、F-VS5、F-I1）；
3. **可靠性**（心跳接线、事件合并回退、虚拟实体事务、文件恢复/清理）；
4. **配置化**（所有硬编码超时/阈值/批量/质量分）；
5. **文档治理**（所有 D-*）；
6. **性能与优化**（串行 embed、分页、SQL 化、死表清理）。

我明确**不会做**的事：

- 不引入云依赖，不改变"本地优先"；
- 不破坏现有 API 契约（除非你明确同意加字段/改状态码）；
- 不一次性大重构，按阶段小步走、每步 `cargo check`；
- 不把"文档没写"当成"可以随便改"——设计意图优先于文档。

## 十、需要你确认的关键设计问题（8 条）

1. **字典库边界**：是否严格 append-only？文件全文删除、事件归档是否允许物理删除字典数据？
2. **同步/异步等价**：是否接受抽统一 MemoryWriter 的中等重构？还是先最小补丁？
3. **Agent 身份**：唯一权威 owner_id 是配置 `primary_agent_id`（默认 `primary_agent_default`），还是固定 `"primary_agent"`？
4. **一致性模型**：是否要求跨三库强事务？还是接受"字典库权威 + 索引可重建/补偿"？
5. **心跳自适应**：本版本是否必须实现？还是"固定间隔 + 可配置"即可？
6. **冷数据语义**：归档数据默认是否参与普通搜索？`include_archived` 默认值？
7. **文件向量**：删除时物理删除，还是标记失效由心跳清理？
8. **API 契约**：是否允许增量加字段（如 `queued`、owner 校验参数）？还是必须完全保持现状？

## 附：我目前最不确定的三点

1. **字典库的"永不删除"是否绝对**——文件全文删除是现有行为，可能与"永久存档"冲突。
2. **Agent owner 的历史语义**——`"primary_agent"` 是早期默认值，还是某个真实 agent 的 id？
3. **事件合并失败是否应该回退创建新事件**——我倾向"必须回退"，但如果你希望"宁可丢弃也不产生重复"，逻辑要反过来。
