## 一、项目定位：Agent 的外挂记忆子系统

- 守心不是给人用的笔记软件，而是**给智能体额外挂载的一套记忆系统**。
- 输入是**智能体与用户的对话**；智能体的内部思考/推理**不算**，不写入。
- 所有对话（用户发言 + 智能体最终发言）都要进入系统，由系统自动拆解为人物、事件、待办、事实、学习素材。
- 它和智能体是**并行关系**：智能体正常对话/总结，顺手把内容丢给守心；守心不阻塞智能体。

**设计价值观（修正后）**：

1. **原文绝对不丢**：字典库是源文件，任何情况下不删除。
2. **写入绝不阻塞智能体**：写入路径只做落盘 + 入队，处理慢没关系。
3. **最终可查 > 实时一致**：智能体稍后通过接口拿到"已经梳理好的记忆"。
4. **自动化 > 手动整理**，但自动化必须可观测、可恢复、可解释。
5. **本地优先 > 云端能力**：当前本地 Llama，未来换更强本地模型。
6. **有界资源 + 主动维护**：热/冷分离、心跳巡检、主动提醒。

## 二、运行模型：并行、异步、最终一致

典型场景（用户举例）：

```
智能体与用户连续对话 100 句（50 轮）
  → 智能体每说一句/用户每回一句，都"无脑"丢进守心
  → 守心只做：原文落字典库 + 入队，立即返回
  → 后台按自己的速度慢慢提取、梳理、入库
  → 智能体之后查询时，拿到的是"此前已经处理好的记忆"
  → 刚丢进去的几句，可能还没出现在查询结果里
```

**设计契约**：

1. **写入不等待 LLM**，不因为处理慢而阻塞对话。
2. **允许积压**：100 句对话产生 100 条待处理记录是正常的，系统要能排队、逐步消化。
3. **读是快照**：返回已提交的派生数据，不承诺包含最新写入。
4. **状态可查**：`extract_status` 让调用方知道某条对话处理到哪一步。
5. **可恢复**：进程重启后，未处理的原文仍能从字典库/队列找回。

> 这意味着"实时记忆"不是目标，"不丢 + 最终可查 + 可观测"才是目标。

## 三、三库：唯一源文件 + 派生索引

| 库 | 角色 | 数据 | 删除语义 |
|----|------|------|----------|
| 字典库（Sled） | **所有记忆的源文件** | 对话原文、`ContactTotal`、`ContactEventRecord`、文件全文 | **绝对不可删除**，只追加 |
| 关系库（SQLite） | 从字典库提炼的结构化索引 | `ContactIndex`、`EventIndex`、`TodoItem`、`FileIndex`、别名、待合并 | 可归档/逻辑删除，可重建 |
| 向量库（HNSW/Embedded） | 从字典库提炼的语义索引 | 学习素材、事件 embedding、文件 chunk | **物理删除由心跳执行**，可重建 |

**核心契约**：

1. 字典库是 source of truth，**任何 API 的"删除"都不能物理删字典**。
2. 关系库/向量库是派生数据，可以清理、重建；删除它们不影响源文件。
3. 文件删除：字典里的全文保留，关系库标记删除，向量由心跳物理清理。
4. 事件清理：字典里的事件历史保留，关系库归档/失效，向量由心跳清理。

## 四、写入主链路：无脑落盘 + 慢处理 + 强事务提交

```
add(对话)
  → 最小校验（长度/owner）
  → 字典库追加原文（幂等）
  → 入队（sled 持久化）
  → 立即返回 conversation_id + 处理状态
  → 后台 worker：LLM 提取 → 清洗 → 统一写入层
  → 三库强事务提交（派生数据全可见或全不可见）
  → 状态 completed / failed（可观测）
```

**设计契约**：

1. add 不做同步 LLM，不做重校验；"无脑丢"是设计，不是偷懒。
2. 字典库是"真源"，队列是"缓冲"；入队失败不应导致原文丢失，可由**对账/扫描**从字典库恢复未处理对话。
3. 处理结果落三库必须**强事务**（见下一章）。
4. 读接口只返回已提交数据；未提交的派生数据不可见。
5. 失败可重试；重试幂等，不产生重复联系人/事件/向量。

## 五、强事务模型（你要求：不能降级）

三库没有共享事务引擎，所以"强事务"在实现上是：

> **WAL + 两阶段提交 + 幂等重放 + 可见性控制**，对外表现为"派生数据全有或全无"。

**事务边界**：不是 `add` 原文，而是**提取结果落三库**这一刻。

**提交步骤（提案）**：

1. sled 写 `commit_intent(tx_id, conversation_id, state=prepared)`。
2. 字典库追加派生记录（幂等；字典不可回滚，允许先于索引存在）。
3. SQLite 开启事务，写入联系人/事件/待办/文件等关系数据（不提交）。
4. 向量写入带 `tx_id` 的暂存状态（或 staging 命名空间，默认不可见）。
5. 提交：SQLite commit → 向量标记可见 → `commit_intent` 置 `committed`。
6. 失败/崩溃恢复：回滚 SQLite、删除暂存向量、intent 置 `aborted`；字典原文保留，可重新提取。

**关键点**：

- **可见性**：读者只看到 `committed` 的关系数据与向量；`prepared` 状态对查询不可见。
- **幂等**：`tx_id = conversation_id + extraction_version`；重放覆盖/跳过，不产生重复。
- **字典例外**：字典是 append-only，不能回滚；允许"原文已存在、索引尚未提交"的中间态，这是设计允许的，不是弱化事务。
- **不降级**：任何一步失败都中止提交并重试，绝不把"部分写入"暴露给读者。

> 需要你确认这个"强事务"的边界是否符合预期（见第十二节）。

## 六、Owner / Scope：隔离是硬约束

- **唯一权威**：Agent 的 owner_id 来自配置 `primary_agent_id`（默认 `primary_agent_default`），不再使用散落的 `"primary_agent"`。
- 所有 owner 解析走同一入口（`Scope::to_owner_params` + 注入的 primary_agent_id）。
- 所有读/删接口必须校验 owner，不能只凭 id 越权。
- `owner_type` 的序列化统一为 `User` / `Agent`，不再混用 `user` / `agent`。
- API 允许增加必要的 owner 校验字段。

---

## 七、生命周期：热/冷、生效日期、升降级、归档降权

- 热表有界（事件、联系人、待办各有上限），冷数据软归档（`is_archived`），**不是物理删除**。
- 事件有自己的**生效日期/失效日期**（`auto_invalid_at`），到期失效。
- 事件可**升级/降级**（被引用多 → 提升；长期不用 → 降级），且必须在清理之前执行。
- **归档数据默认参与检索，但优先级降一级**（不是排除）。
- 字典库里的原始记录不参与"归档删除"，只影响关系库/向量库的可见性与排序。

---

## 八、心跳：清洁工 + 资料员（重点章节）

心跳不是普通定时任务，而是系统的"第二层处理"：

**职责一：任务巡检（清洁工）**
- 检查当前待处理任务、过期任务；
- 清理过期/低价值事件、合并重复、归档冷数据；
- 主动提醒："当前还有哪些任务没做"。

**职责二：资料整理（资料员）**
- 基于**已经分解整理好的记忆**，提取关键信息；
- 更新联系人表、联系人资料、**用户人设模型（persona）**；
- 维护待办状态与提醒。

**执行结构**：

- **维护阶段**：纯 SQL，快，不调用 LLM（巡检、清理、归档、提醒）。
- **LLM 阶段**：慢，生成/更新画像与人设、发现歧义、生成问题。
- 两阶段可独立触发（`maintenance_only`）。
- **自适应间隔本版本必须实现**：`enabled` / `min` / `max` / `adaptive` / `idle` / `question_pool_dir` 全部真正接线。
- 失败不能卡死 `executing`（`ExecutingGuard` 保留）。

> 心跳的产出不是"日志"，而是**更干净的记忆 + 更完整的联系人人设 + 明确的待办提醒**。

---

## 九、LLM：本地优先、临时模型、未来视觉、输出可信

- **本地优先不变**：当前 GGUF Llama 3.2 3B 是**临时模型**（设备性能限制）。
- 后续会换**更高性能的 Llama GGUF**，专门用于记忆梳理；可能加入**视觉塔**，支持理解图片。
- 因此设计上必须：
  1. 模型可替换、后端可切换，prompt/参数不绑定 3B；
  2. 预留图片/多模态输入（文件处理、提取接口、存储结构）；
  3. 本地 GGUF 是默认路径，云端 API 只是可选备选；
  4. LLM 输出默认不可信，必须 sanitizer + JSON 校验 + 正则兜底，**最终写入的必须是可信结构化数据**；
  5. 心跳 LLM 与主 LLM 隔离，心跳失败不拖垮主链路。

## 十二、v2.1 最终确认（用户 2026-10-28 补充）

### 12.1 强事务边界：add 也必须原子

- **不只是"提取结果落三库"要强事务，`add` 的"原文落库 + 入队"也必须是强事务。**
- 实现基础：字典库与 `pending_tasks` 树在**同一个 sled DB**，用单个 `sled::Transaction` 同时写：
  - `ConversationRecord`（原文）
  - `ExtractionTask`（pending 任务）
- 要么都成功，要么都失败；不再把"入队失败后扫描字典恢复"当作主保障，扫描只作为**兜底对账**。
- 推论：生产路径必须使用带持久化队列的构造方式；`BackgroundTaskQueue::new()` 这种非持久化实例应移除或标记 test-only（D-M6）。

### 12.2 字典库：不可物理删除，但允许标记

- **绝对禁止物理删除**任何字典数据。
- **允许加逻辑标记**（tombstone，如 `deleted_at` / `is_deleted`）。
- 删除 API = 在字典记标记 + 删/归档派生索引；原文永久保留。
- 文件删除：字典全文保留并标记；关系库 `file_index` 标记删除；向量由心跳物理清理。

### 12.3 归档检索：热表优先，归档兜底，不做分区

- 归档数据**不在热表**，设计目的就是让智能体**快速拿到热数据**，而不是一上来扫海量历史。
- 不做单独分区；只作为查询规则：
  1. 默认只查热表（快路径）；
  2. 热表结果不足时，才以**低优先级**补充归档数据；
  3. 归档数据永远排在热数据之后，不参与默认首屏结果。
- 这比"归档参与检索并降权"更精确：**热优先、冷兜底**。

### 12.4 心跳处理范围：待办 + 过期 + 积压

心跳的"任务巡检"包括：

1. **待处理任务**：当前 pending 的待办/事件；
2. **过期任务**：已过 deadline/生效期的任务，主动标记（`auto_invalid` / expired）；
3. **提取积压**：未处理的对话/队列积压（系统级 pending）。

用户例子：本月 23 号要买火车票，今天 24 号，任务已过期；即使智能体还没拿到这条记忆，心跳也要**主动把过期任务标出来**，而不是等智能体查询时才处理。

### 12.5 人设更新频率：每个联系人每天 2 次

- 是**每个联系人**每天最多 2 次画像/人设更新，不是整个联系人表共 2 次。
- 保持按 `contact_id` 维度计数（现有 `can_update_profile` / `contact_profile_update_log` 方向正确），并做成可配置。

### 12.6 视觉塔：先预留，后对接

- 现在**预留**图片/多模态输入接口与存储字段（如 `media_type`、`image_path`、多模态 message）。
- 等选好更强的 GGUF 模型后，再对接视觉塔，不提前绑定具体模型能力。

### 12.7 最终定位再强调

> 这个记忆系统是**给智能体准备的**，不是面向用户的。
> 它是智能体的**外部记忆系统**，完全为智能体服务：把记忆留在本地，整理成**高质量、可快速取用**的记忆信息。

设计含义：

- API 优先服务智能体取用（快、结构化、可分页/过滤），不按人类 UI 设计；
- "高质量"优先于"全量堆砌"：心跳的资料员职责、人设模型、去重/合并都是为质量服务；
- 本地优先不变；智能体是唯一主要调用方。
