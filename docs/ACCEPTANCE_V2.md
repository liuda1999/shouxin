| # | 审计项 | 判定方式 |

## 3. 六项审计结论

### 3.1 API 全功能覆盖 —— ✅ 28/28 = 100%

覆盖的端点：`/health`、`memory/add`、`extract_status`、`search/{semantic,events,contacts,history}`、
`search/smart`、`contacts/:id/detail`（含 `since`）、`vector/search`、`todos`（GET/POST/PUT/DELETE）、
`events/pending_merges`、`heartbeat/{status,pending_questions}`、
`virtual_entities`（GET/POST/GET:id/PUT/DELETE/check）、`files/upload`（GET 元数据 / GET 文本）。

> 两项协议细节在审计中确认：`POST /api/files/upload` 只接受 `application/octet-stream` 原始字节流
> （文件名走 query），multipart 会被 415 拒绝；`/api/vector/search` 与 `/api/memory/search/semantic`
> 是同一个 handler，请求体是 `{query, limit, user_id}` 而非向量数组。

### 3.2 联系人创建 —— ✅ 通过（召回 84.8%，捏造 0）

- **164 条联系人**，覆盖 46 个期望唯一人名中的 39 个（**84.8%**）；
- **凭空捏造 0 条**：所有姓名或别名都能在语料原文里逐字找到；
- 未命中的 7 个：

| 名字 | 原因 |
|------|------|
| 孙悟空 / 林黛玉 / 哆啦A梦 / 福尔摩斯 | **不算漏检**：虚拟角色走独立表，本就不在联系人表（设计如此） |
| 滕飞 / 白露 / 唐棣 | 真实漏抽（只在单条语料出现一次，模型未识别为人名） |

### 3.3 别名识别 —— ✅ 93.3%（42/45）

两个口径一致：

| 口径 | 结果 |
|------|------|
| 别名被抽进主名记录的 `aliases` | **42 / 45 = 93.3%** |
| 用别名检索能命中同一个 `contact_id` | **42 / 45 = 93.3%** |

未命中的 3 个：`包蓉/蓉蓉`、`滕飞/飞哥`、`黎晚/Nora` —— 前两个对应的人本身没建上档，第三个英文名未被保留。

### 3.4 画像与人设 —— ✅ 机制通过，覆盖率 23.8%（受算力限制）

| 指标 | 结果 |
|------|------|
| 生成画像 | **39 / 164 = 23.8%** |
| 合法 JSON + 5 个必备字段 | **39 / 39 = 100%** |
| 本轮新增 | 39 条 |
| 本轮更新 | **0 条**（尚未跑到第二轮，见下） |

画像结构（抽样，`房晓`）：

```json
{
  "personal_info": {"name":"房晓","aliases":["Milo","晓晓"],"known_occupation":"工程师",
                    "known_interests":["数据迁移","供应商比价"]},
  "social_relations": [{"relation_type":"上级","related_contact_name":"滕飞","confidence":0.9}],
  "major_events": [...], "objective_evaluation": "...", "potential_relations": [...]
}
```

对应 `contact_index`：`relationship_tags=["上级","室友"]`、`related_contact_ids` 非空 —— 画像与索引是对上的。

**关于"更新"**：更新判定是 `last_interaction_at > 上次画像时间`，
需要"画像已生成 + 该联系人又被提到"才会触发。本轮画像只跑了 50 分钟就停了，
没进入第二轮，所以观察不到更新。这条逻辑有单测覆盖，但**本轮未取得实际更新样本**，如实记录。

**覆盖率只有 23.8% 的原因**（不是失败）：
1. 3B/4B 模型在纯 CPU 上生成一个画像约 45–90 秒，164 个联系人需约 2–4 小时；
2. 心跳每轮只处理 3 个联系人，且**歧义检测会抢占预算**（见 4.5）；
3. 画像在后台可继续跑，不需要人工干预。

### 3.5 多联系人关系 —— ⚠️ 机制通过，准确率 47.6%（可评估口径）

| 口径 | 结果 |
|------|------|
| 全部关系对 | 10 / 37 = 27.0% |
| **可评估**（至少一方有画像） | **10 / 21 = 47.6%** |

机制是通的：画像的 `social_relations[].related_contact_name`
→ `find_contact_id_by_name_same_owner` 解析成 ID → 写入 `contact_index.related_contact_ids`
→ `GET /api/contacts/:id/detail` 的 `related_contacts` 能读出来。

准确率偏低是**模型能力**问题，抽样可见具体错法：

```
期望：沈亦舟是程澜的直属上级
实际：沈亦舟的画像写的是「上级 → 路遥」（对象抽错，路遥是另一条语料里的人）
```

另有把**本人别名当成他人**的情况：

```
房晓 的 social_relations 里出现 "室友 → Milo"（Milo 是房晓自己的英文名）
汤沐 的 social_relations 里出现 "同事 → 小汤"（小汤 是汤沐自己的别名）
```

### 3.6 时间线索引 —— ✅ 通过（这是用户提出的"近一个月"场景）

| 指标 | 结果 |
|------|------|
| detail 返回的事件带时间 | **15 / 15 = 100%** |
| `since=30d` 过滤正确 | **8 / 8**（结果都是全集子集，且每条事件时间都在 30 天内） |

抽样（沈亦舟）：

```
全部事件 3 条 → since=30d 返回 2 条（丢掉了去年十一月那条）
stats.since 回显 2026-09-29T23:56:25Z，调用方可确认过滤生效
```

调用方式：

```bash
curl "http://127.0.0.1:3000/api/contacts/<id>/detail?user_id=acc3&since=30d&event_limit=50"
```

返回的每条事件都带 `event_time` 与 `time_range_start`，
即使不传 `since`，客户端也能自己按时间筛。

## 4. 本轮发现并修复的缺陷

| # | 级别 | 问题 | 修复 |
|---|------|------|------|
| 4.1 | **P1** | 事件时间只按 ISO 8601 解析 `time_info`，遇到"上周三"直接失败并回落到**写入时间**，所有历史事件看起来都发生在今天 | 新增 `resolve_event_time`：`time_info` → `time` 字段 → 事件描述 → 对话原文，逐级降级 |
| 4.2 | **P1** | 时间解析器不支持过去时间（上周三 / 三个月前 / 去年十一月 / 上个月中旬） | 补齐过去时间解析，含中文数字（"三个月前"），11 项单测覆盖 |
| 4.3 | P2 | 模型把时间词从事件描述里删掉时，没有任何兜底 | 加"对话原文"兜底（对话里通常只有一个时间表达） |
| 4.4 | P2 | 人名过滤漏掉句子碎片（"别忘""前采购服""本周五之""接口文档"），它们抢占画像候选位却永远生成不出画像 | 过滤规则补三类：时间短语、动词前缀、事物词；单测同步扩充 |
| 4.5 | **P1（未修）** | 歧义检测把**不同人的别名**混成一人（"小程/老傅/北哥"被当成程澜），并且重复创建"已存在"的待办 20+ 次，把整轮心跳预算吃光，导致画像不推进 | 已在报告中记录，本轮未改（涉及歧义检测的提示词与去重策略） |
| 4.6 | P2（未修） | 画像生成遇到空响应时按"每日上限 30 次"重试，一个坏联系人会反复占用名额 | 建议改为"连续失败 2 次即跳过"，本轮用手工标记绕过 |
| 4.7 | P2（未修） | 事件合并只更新 `contact_ids`，**不更新时间**，导致重放旧事件无法修正历史时间 | 建议合并时若旧时间为空或等于创建时间则采纳新时间 |

## 5. 结论

**能投入日常使用**，但有三条边界需要知道：

1. **联系人与别名非常稳**：164 条联系人、0 捏造、别名识别 93.3%、同名可区分。
2. **画像/关系机制可用，但慢且受模型能力限制**：
   - 画像 JSON 100% 合法；
   - 关系写入链路通，但对象准确率约一半（3B/4B 模型把关系对象抽错）；
   - 覆盖率受 CPU 算力限制（164 个约需 2–4 小时），且会被歧义检测抢占预算。
3. **时间线（近一个月）可用**：事件 100% 带时间，`since=30d` 过滤正确。

**建议的下一步**（按性价比排序）：

1. 修 4.5（歧义检测去重 + 不混人），它同时影响画像覆盖率与待办质量；
2. 修 4.6（失败 2 次即跳过），避免坏数据卡住队列；
3. 修 4.7（合并时更新时间），让历史事件时间可被修正；
4. 关系抽取改用 8B 以上模型或 API 后端 —— 47.6% 的主要瓶颈是模型，不是代码。
